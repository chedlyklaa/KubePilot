## Reasoning

- **Discovery** (2/2 reached the 0.9 confidence+evidence bar): the personas with unambiguous, directly-observable evidence (transient crash logs, OOM kill reason, image-pull error text) were investigated to full confidence quickly. Personas requiring interpretation across multiple weak signals typically needed more tool calls before confidence cleared 0.9.
- **Fixed** (0): mostly the personas with a single, unambiguous, kubectl-expressible remedy — transient crash (restart), OOM (memory raise), bare pod (delete), flaky dependency (restart).
- **Escalated** (1): personas where no kubectl command can address the root cause (bad image tag, external third-party outage) correctly routed to escalation rather than an automated attempt that could never succeed — the intended behavior of Guardian's REJECT/DELEGATE_HUMAN split and Policy's immediate-escalation routing for DELEGATE_HUMAN.
- **Blocked** (0): steps that needed human approval (high risk / non-reversible / production tier elevating risk) — the harness auto-approved these rather than letting them hang, so a 'blocked' outcome here means a real denial-equivalent condition (Policy rejecting after Guardian's own review), not a stuck approval.
- **No automated fix available** (1): the Planner concluded every step should be command-less (its own way of saying "nothing safe to run automatically"). This routes straight to Reflexion, skipping Guardian/Policy — and a real gap surfaced by this test run: the top-level workflow state's `outcome` field stays `null` on this path rather than being set to something explicit, even though Reflexion's own internal bookkeeping treats it as a failure. Worth a small fix in graph.js if this path matters for monitoring.
- **False positives** (0/2 false-positive tests): the P8 persona fed the Orchestrator's original (stale) signal as the incident while making live pod state show a fully healthy, already-resolved pod. The pipeline correctly recognized the contradiction in both clusters and did not apply an unnecessary fix — Guardian's §7.5 live-state re-fetch (stateDrift detection) is exactly the mechanism designed to catch this, and it did.
- **Tier effect (minikube/dev vs cluster2/production)**: for the same persona, compare each pair's `approvalsRequested` and `policy.status` — production tier's risk elevation (MEDIUM→HIGH, and non-reversible steps always requiring approval) should show more approval requests on cluster2 than the identical minikube incident, even though Guardian's verdict on the underlying command is usually the same.
