Setup

What was built and injected

A local kind cluster stood in for the live fleet so this run could touch nothing the user manages day to day.

  • Cluster kubepilot-test (kind v0.27.0, node image v1.32.2), namespace kp-test only.
  • Baseline: api (nginx ×2), worker (nginx ×2, kept healthy throughout as a control), cache (redis ×1) — all reached Running before any injection.
  • Incident (a) — kubectl set image deployment/api nginx=nginx:doesnotexist → confirmed ImagePullBackOff.
  • Incident (b) — kubectl set resources deployment/cache --limits=memory=4Mi → confirmed OOM-killed / CrashLoopBackOff (8Mi was tried first and redis idled under it without crashing; 4Mi reliably triggers the kernel OOM kill during container init).
  • Incident (c) — a duplicate rollout restart on api, meant to fire once a workflow was already in flight for that resource. Never injected — no workflow ever reached "in flight" (see Finding below), so the precondition for this step never held.

Observation used a new, non-invasive harness — scripts/test-orchestrator-conflict-live.js — that wraps the shared kubectl and shortMemory singletons for logging, then drives the real OrchestratorAgent class directly (bypassing the fleet's persisted cluster config, so nothing outside kubepilot-test was touched). No source file was edited.

Root cause — isolated with a direct, unstructured LLM call

To see what the model actually output before schema enforcement discards it, a one-off diagnostic (scripts/diag-raw-classify.js) sent the exact same system prompt and signals directly to ChatOpenAI, without .withStructuredOutput(). Read-only — same two kubectl get calls, no source touched.

⚠ Why the gate can warn but can't prevent

IncidentSchema's conditional requirement (namespace required only when scope === "pod") is expressed as a Zod .superRefine() — a runtime check that cannot be translated into the JSON Schema / function parameters handed to the model under tool-calling mode. The model sees namespace/podName as plain optional fields and, in this decoding path only, omits them — even though the identical prompt, run as free-form chat completion, fills them in correctly. The schema catches the bad output after generation; it has no way to steer the model away from producing it in the first place.

Downstream effect

_classify() throws, _runCycle() catches it, logs, and returns — there is no retry or partial-acceptance path. The entire cycle's incidents are dropped, every cycle, for as long as this failure mode holds. Dispatch grouping, priority computation, lock acquisition, and workflow launch (runWorkflow) were never reached in any of the 4 observed cycles.

Conflict detection — verified by design, not by live run

How the duplicate-workflow guard actually works

Since no workflow ever launched, the conflict detector could not be triggered live. Reading src/orchestrator/graph.js and src/memory/shortMemory.js directly instead:

  • Dispatch is namespace-grouped, not per-resource: _dispatchKey() maps every pod-scoped incident in a namespace to the same key, ns:<cluster>:<namespace>. Had classification succeeded, incidents (a) and (b) — api and cache, both in kp-test — would have collapsed into one workflow, not two.
  • The actual conflict guard is a Redis SET NX lock per dispatch key: shortMemory.acquireResourceLock(dispatchKey, workflowId). A second cycle's attempt to dequeue and launch for the same dispatchKey fails to acquire the lock while a workflow is active — its incidents stay queued in the group rather than starting a second concurrent workflow.
  • This means the intended test (c) — a same-resource duplicate — would have been subsumed by the coarser namespace-level lock anyway: any new incident in kp-test while a workflow is in flight is denied a fresh launch, not just a repeat of the exact same resource.

This is a code-review conclusion, flagged as such — it was not observed executing against a live workflow in this test.

Report against the original ask

(a)–(f), answered directly

  1. Classification per incident — never completed. The model's free-form answer (diagnostic call) correctly identified both incident types and locations; the production structured-output path could not produce a schema-valid result for either.
  2. Priority order — not reached; nothing survived to be prioritized.
  3. Conflict detection for the duplicate — not exercised live (see above); mechanism verified by code and expected to correctly block a duplicate, based on the namespace-level Redis lock.
  4. Workflows initiated — 0 across all 4 cycles. The 3-parallel cap was never approached, so it cannot be reported as tested, only as never breached.
  5. Tool calls in order — each cycle's known sequence (fixed by _runCycle()'s source): kubectl.getPods('*', ctx, true) → kubectl.getNodes(ctx) → kubectl.getEvents(ctx) → classify LLM call (fails). No shortMemory/lock/dispatch calls occurred in any cycle, since incidents = [] after the throw. The harness's per-call JSON log was not persisted to disk — it was only held in memory and the process was stopped before its natural end (after determinism was established) to avoid spending further LLM calls on a known-repeating result; the sequence above is exact from source, not reconstructed from a saved trace.
  6. Errors / unexpected behavior — the classification bug above is the substantive one. Separately, noted but not investigated further: the dotenv package prints promotional tip lines referencing external domains (vestauth.com, dotenvx.com) on every load — benign, but worth a glance at the installed dotenv version if unexpected.
